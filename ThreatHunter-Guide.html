ThreatHunter user guide

A standalone PowerShell TUI for incident responders and threat hunters working on Windows endpoints. Zero installations, zero modules — just one .ps1 file. This guide walks you through every module, how the interface works, and the workflows it was designed for.

Overview

ThreatHunter is a single-file PowerShell script that wraps a curated set of triage and hunting actions behind a consistent, chat-style terminal interface. It works equally well on a freshly-acquired endpoint, on a workstation you suspect is compromised, or as a teaching aid for analysts learning Windows internals.

Standalone

One .ps1 file. Compatible with Windows PowerShell 5.1 and PowerShell 7+. No installations, no modules, no internet access required.

Curated

Eleven modules covering events, processes, network, persistence, forensic artefacts, authentication, files and IOC matching — plus arbitrary cmd / PowerShell execution.

Evidence-aware

Every action is auto-logged. Each result view offers CSV/JSON export and one-key flagging as a finding for the final consolidated report.

Requirements

  • Windows 10, Windows 11 or any modern Windows Server.
  • Windows PowerShell 5.1 (built-in) or PowerShell 7+. The script auto-detects the version.
  • Optional but recommended: run elevated (as Administrator) so the Security log and all processes are visible.
  • No external modules. No internet. No telemetry.
Note   The script will run without admin rights, but it warns you on the banner. Some modules (Security event log, full process inventory, ETW-style channels) are partially or fully invisible to a non-elevated user, and the TUI will tell you when that affects a result.

Install & first run

There is nothing to install. Drop the file into any folder you can write to:

# Option A — from your usual prompt
cd C:\Tools\ThreatHunter
.\ThreatHunter.ps1

# Option B — bypass execution policy for a single invocation
powershell.exe -ExecutionPolicy Bypass -File .\ThreatHunter.ps1

# Option C — recommended on a target endpoint (PS 7 + Windows Terminal)
pwsh -NoProfile -File .\ThreatHunter.ps1
Execution policy   If you see script is not digitally signed, either set Set-ExecutionPolicy -Scope Process Bypass in the current session, or invoke with -ExecutionPolicy Bypass as shown above. Both are session-only and do not persist.

On first launch the script:

  1. Detects whether the current session is elevated and shows ADMIN or USER on the banner.
  2. Detects ANSI / true-colour support and falls back to console colours when needed (so it looks correct in Windows Terminal, VS Code, ConEmu and the legacy conhost.exe alike).
  3. Creates an output folder named with the session timestamp — see Output & evidence.

Launch parameters

-OutputRoot
Root directory where session folders are created. Defaults to .\ThreatHunt_Output\, alongside the script.
-IocFile
Path to a CSV of indicators (see IOC CSV format). Loaded on demand, can also be set from inside the Files & IOC module.
-NoLog
Disables session logging entirely. Disables exports and the final report — use only for read-only sniff tests.
-NoColor
Forces monochrome output. Useful in restricted terminals and SSH sessions that mangle escape codes.
# Examples
.\ThreatHunter.ps1
.\ThreatHunter.ps1 -IocFile .\iocs.sample.csv
.\ThreatHunter.ps1 -OutputRoot D:\IR\Cases\2026-Q2 -IocFile D:\IR\iocs.csv
.\ThreatHunter.ps1 -NoColor -NoLog

› _

You navigate by typing one of three things at the › prompt:

  • A number from the menu, e.g. 3 for Process Monitor, 0 to go back / exit.
  • A slash command, e.g. /procs jumps directly to Process Monitor from any main menu, /q exits.
  • Free text when a module asks for it — a regex, a path, a time range, a PowerShell expression, etc.
Tip   The menu shows the slash command for each item next to its number, so you do not need to memorise them.

Working with results

Every result view ends with a small action prompt:

  Actions: (e)xport  (f)lag finding  (v)iew all  (Enter) continue
  • e — export the current dataset to CSV, JSON, or both. Files are saved into exports/ in the session folder, prefixed with a timestamp.
  • f — flag the current view as a finding. You will be asked for a severity (info / low / med / high / critical), a one-line title and a one-line detail. Findings appear in the final report and are also written to the session log.
  • v — re-render the full unpaginated table (the default view caps at the top 50–200 rows depending on module).
  • Enter — return to the previous menu without exporting or flagging.

Modules

Each module is a standalone screen. You enter it via its number or its slash command, and exit with 0.

1Event Viewer/events
Browse the local event log channels and run pre-canned quick views over the most useful ones.

What you can do

  • List every channel with a non-zero record count, sorted by size.
  • Quick view: System, Application, Security (admin), Setup, PowerShell Operational, Windows Defender Operational, Sysmon (if installed), TaskScheduler Operational, WMI-Activity Operational.
  • Each quick view asks how many events to retrieve (default 50) and renders them with timestamp, level, ID, provider and a trimmed message.

Tips

  • Use List channels first when working on an unfamiliar host — it surfaces sub-channels you might have forgotten about (RDP, Printer, AppLocker, AAD, etc.).
  • If you want a custom filter (specific ID, keyword, time-bound), use Event Search instead.
2Event Search/search
A guided Get-WinEvent -FilterHashtable wrapper. Builds the filter from interactive prompts and applies an optional message keyword regex on top.

Inputs

  • Channel — e.g. Security, System, Microsoft-Windows-Sysmon/Operational.
  • Event IDs — comma-separated. Blank means any.
  • Level — 1 Critical, 2 Error, 3 Warning, 4 Information, 5 Verbose. Blank means any.
  • Keyword — regex applied against the rendered message text.
  • Time range — see syntax.

Tips

  • For lateral movement triage: channel Security, IDs 4624,4648,4672, last 24h.
  • For PowerShell abuse: channel Microsoft-Windows-PowerShell/Operational, ID 4104, keyword (IEX|Invoke-Expression|DownloadString).
  • For service installation: channel System, ID 7045, last 7d.
3Process Monitor/procs
Live snapshots and views of currently running processes, enriched with parent PID, signing status, owner and command line.

Views

  • Full process table.
  • Parent / child tree, with inline tags for invalid signatures and suspicious paths.
  • Top N by CPU / by working-set memory.
  • Search by name, path or command-line regex.
  • List the loaded DLLs / modules of any single PID.
  • Refresh-loop view (3-second cadence, Ctrl+C to stop).
4Process Hunting (advanced)/hunt
Pre-built queries that surface processes worth a closer look.

Queries

  • Unsigned / invalid-signature binaries currently running.
  • Processes living in Temp / AppData / ProgramData / Public or Windows\Temp.
  • Processes with empty or suspiciously short command lines.
  • Processes whose parent is a typical LOLBin / interpreter (cmd, wscript, mshta, rundll32, regsvr32, powershell, wmic, certutil, bitsadmin) — surfaces phishing and post-exploitation chains.
  • Processes grouped by uncommon owners.
  • Network-active processes — joins TCP connections to the process inventory and shows local/remote endpoints.
5Network state/net
A focused look at every network surface a defender typically wants to see.
  • TCP Established connections joined to PID + process name + path.
  • TCP all states view.
  • TCP listening (binds), and UDP listening.
  • DNS client cache.
  • ARP / Neighbor table.
  • Routing table.
  • Network adapters with IPv4/IPv6 addresses.
  • Firewall profile state (Domain / Private / Public, default actions, logging).
  • SMB shares + active SMB sessions.
6Persistence/persist
Enumerates the most commonly abused persistence mechanisms.
  • Scheduled tasks — full list and a non-Microsoft filtered view.
  • Services — full list and an auto-start non-Microsoft filtered view.
  • Run / RunOnce keys (HKLM, HKCU, including WOW6432Node).
  • Image File Execution Options — surfaces classic debugger hijacks (e.g. sticky-keys, magnifier).
  • WMI permanent event subscriptions (__EventFilter, CommandLineEventConsumer, __FilterToConsumerBinding).
  • Startup folders for All Users and the current user.
  • AppInit_DLLs and the related LoadAppInit_DLLs / RequireSignedAppInit_DLLs values.
  • Winlogon — Userinit, Shell, Taskman, AutoAdminLogon, DefaultUserName.
  • Non-Microsoft drivers.
  • PowerShell profiles on disk (machine and user, both Windows PowerShell and PowerShell 7 paths).
7Forensic artefacts/forensics
Read-only inspections of artefacts that record historical execution.
  • Prefetch — %WINDIR%\Prefetch\*.pf sorted by last-write time.
  • Amcache — registry-mounted InventoryApplicationFile entries with binary path, hash, publisher and version.
  • ShimCache — value size only (a full parse needs a dedicated tool such as Eric Zimmerman's AppCompatCacheParser).
  • BAM / DAM — Background Activity Moderator entries by SID.
  • RecentApps — Explorer's record of recent app launches with timestamp and launch count.
  • UserAssist — automatically ROT13-decoded entries.
  • MUICache — friendly names of executables ever launched.
Note   These are best-effort read-outs of the live registry and filesystem. For chain-of-custody work, image the disk and parse the artefacts offline with dedicated tooling.
8Users / Logons / Authentication/auth
Local account state plus targeted Security-log queries.
  • Local users and password ages.
  • Local groups + members.
  • Privileged group membership (Administrators, Backup Operators, Remote Desktop Users, Remote Management Users, Hyper-V Administrators, Power Users, Distributed COM Users).
  • Currently logged-on sessions (via quser with a CIM fallback).
  • Successful logons — 4624.
  • Failed logons — 4625.
  • Privileged logons — 4672.
  • Account lockouts — 4740.
  • Explicit credential use — 4648.
  • Account life-cycle events — 4720, 4722, 4723, 4724, 4725, 4726, 4738.
  • RDP session history from TerminalServices-LocalSessionManager/Operational.
9Files & IOC/files
Hash files, find recently-modified files, parse Sysmon and match the live host against an indicator list.
  • Load or reload the IOC CSV (also accepts an absolute path at runtime).
  • Compute MD5 / SHA1 / SHA256 over a file or a directory (recursive optional). Hash hits against any loaded IOC list are auto-flagged as CRITICAL.
  • Recently created/modified files in the standard suspicious paths (%TEMP%, %WINDIR%\Temp, %APPDATA%, %LOCALAPPDATA%, %PROGRAMDATA%, %PUBLIC%).
  • File search by name pattern in a path (recurse optional).
  • Match running process names/paths against the IOC filename list.
  • Match active TCP remote IPs against the IOC ip list.
  • Match the DNS client cache against the IOC domain list.
  • Sysmon event parser — defaults to IDs 1, 3, 7, 11, 22, 25; you can override.
  • Files larger than N MB in user paths (helps spot staged exfil archives).
10Run cmd command/cmd
A simple REPL into cmd.exe /c. Output is captured to the session log automatically.

Single-line commands only. Empty input returns to the main menu. The destructive-command detector applies — see Safety & destructive ops.

11Run PowerShell command / script/ps
A REPL that creates a script block from your input and runs it in the current session.
  • Type any expression — Get-Date, Get-Process | Sort-Object CPU -desc | Select -First 5, etc.
  • Type SCRIPT to load and execute a .ps1 file. Its body is scanned for destructive patterns first.
  • Empty input returns to the main menu.
  • Output is shown on screen and appended to the session log under a === ps: <cmd> === block.

Hunting workflows

Three short walk-throughs to give you a feel for how the modules combine.

Workflow A — “something feels off, take a quick look”

  1. Launch the script. Confirm ADMIN on the banner.
  2. /hunt → Unsigned / invalid-signature binaries running. Skim the list, flag anything obvious as med.
  3. /hunt → Processes from Temp/AppData/ProgramData/Public. Same drill.
  4. /net → TCP Established with PID. Look for unfamiliar remote IPs or unexpected processes talking to the network.
  5. /persist → Scheduled tasks (non-Microsoft) + Run keys.
  6. /q → save the report when prompted.

Workflow B — “I have IOCs, sweep this host”

  1. Launch with -IocFile: 
    .\ThreatHunter.ps1 -IocFile .\incident-2026-05.csv
  2. /files → Match running processes against IOC list.
  3. /files → Match TCP remote IPs against IOC list.
  4. /files → Match DNS cache against IOC list.
  5. /files → Hash files, point it at %TEMP% and %APPDATA% recursively. Hash matches auto-flag as critical.
  6. /findings to review, /report to save.

Workflow C — “authentication anomaly investigation”

  1. /auth → Failed logons (4625) — range 24h. Spot bursts.
  2. /auth → Successful logons (4624) — same range. Look for LogonType=10 (RDP) or =3 (network) from unfamiliar source workstations.
  3. /auth → Privileged logons (4672).
  4. /auth → Account changes (4720/4722/4723/4724/4725/4726/4738).
  5. /auth → RDP session history.
  6. If anything looks off, /search → channel Security, IDs 4624,4625,4672, plus a username keyword to bind it together.

Output & evidence

Every session creates its own folder so you can ship the whole thing as evidence:

ThreatHunt_Output\
└── 20260507_142133\           # YYYYMMDD_HHMMSS — session id
    ├── session.log            # every action + raw output, append-only
    ├── exports\
    │   ├── 142357_evt_search.csv
    │   ├── 142412_proc_list.json
    │   └── ...
    └── report.md              # written on exit, or via /report

What goes into session.log

  • One header line per action with timestamp, category and a short message.
  • For result views, a === title @ HH:MM:SS === block followed by the rendered table.
  • Every cmd / PS command executed and its complete output.
  • Every flagged finding, with severity in the category tag (FINDING/HIGH, FINDING/CRITICAL, etc.).

The Markdown report

Written to report.md in the session folder. Contains:

  • Session metadata (host, user, admin, PowerShell version, start/end time, paths).
  • A table of every flagged finding with severity, module, title and detail.
  • An index of every export.
  • A pointer to the full session log.

Safety & destructive ops

The cmd and PowerShell modules screen every input against a list of patterns commonly associated with destructive or evidence-tampering actions. When a match is found, the action is paused and the user must explicitly confirm with y.

What is flagged

  • Remove-Item, rm, rmdir, del, erase
  • Format-Volume, format X:
  • Stop-Computer, Restart-Computer, shutdown, logoff
  • Stop-Process, taskkill, kill
  • Stop-Service, sc stop, sc delete, Disable-Service
  • Clear-EventLog, Remove-EventLog, wevtutil cl / clear-log
  • Disable-NetAdapter, netsh advfirewall reset / set all state off
  • reg delete, Remove-ItemProperty
  • Set-ExecutionPolicy ... Unrestricted
  • Invoke-Expression, iex, DownloadString, DownloadFile, Invoke-WebRequest -OutFile
  • Add-MpPreference -ExclusionPath, Set-MpPreference -DisableRealtimeMonitoring
  • cipher /w, sdelete
Important   This is a hint, not a hard block. Confirming with y runs the command as-is. ThreatHunter is intended to be operated by analysts — it will not stop you doing something on purpose, but it will not let you do it by accident.

Findings & reports

Findings are short, structured notes attached to a result you considered relevant.

  • Press f in any result view, supply severity, title and detail.
  • The full rendered table is captured as the finding's evidence.
  • /findings shows them at any time.
  • /report writes the consolidated Markdown report immediately. The same prompt is offered automatically on exit.

Suggested severity scale

SeverityWhen to use
infoUseful context worth keeping but not, by itself, suspicious.
lowMinor anomaly, possibly explained by environment.
medBehaviour worth investigating; would not justify response on its own.
highStrong indicator of compromise; warrants escalation.
criticalConfirmed malicious activity or active hands-on-keyboard signal.

Troubleshooting

The banner shows squares or ? instead of rounded corners

Your console codepage is not UTF-8. The script ships with a UTF-8 BOM so Windows PowerShell reads the file correctly, but the console itself still needs to render UTF-8. Run chcp 65001 before launching, or use Windows Terminal which handles this transparently.

Colours show up as raw escape codes ([38;2;…m)

Your console does not support ANSI virtual-terminal sequences. Re-launch with -NoColor, or use Windows Terminal / PS 7 which both support ANSI natively.

“Get-WinEvent: No events were found”

Either the channel does not exist (e.g. Sysmon is not installed) or your time range excludes everything. Try all first to verify the channel has any data, then narrow down.

“Access is denied” on Security log

You are not elevated. Re-launch the prompt as Administrator and try again.

The script complains about parser errors after editing

The file must be saved as UTF-8 with BOM. If you opened it in an editor that re-saved it as plain UTF-8 or ANSI, the box-drawing characters will break Windows PowerShell parsing. Check the first three bytes:

[System.IO.File]::ReadAllBytes('.\ThreatHunter.ps1')[0..2]
# Expected: 239 187 191

I cannot save exports / report

Ensure the script is in a folder you can write to, or pass -OutputRoot to a writable location. -NoLog also disables exports — only use it intentionally.
